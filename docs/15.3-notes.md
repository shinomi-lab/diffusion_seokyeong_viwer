## T-01 の観測の限界（仮定）

`core::diffusion::Workspace` の `states` は非公開で、`diffuse` はユーザ状態を外から読めない。そのため T-01 は「累積の合計値（`monte_carlo_average` を系列の先頭 r 個・試行 1 回で呼ぶ）」と「呼び出し後の乱数の位置」で比べる。ノード単位の効用は、`node_contact_matches_core_user_state` で `NodeState::contact` と core の `UserState::contact`（`DecisionAny::utility()`、外部は同じ重みの `DecisionAny` を並走）を `to_bits` で比べて補っている。`n_waves`（`total_step`）は `monte_carlo_average` から取れないため、実物との直接比較はしていない（T-16 の構造検査のみ）。

## 仮定・設計書との小さな差分

- `ScenarioConfig.message_space` は `Vec<MessageSpec>`（`Message` が `Serialize` を持たず、core を改変できないため。`messages()` で `Vec<Message>` に変換）。
- `ScenarioConfig.horizon`（M4 の予算の基準。0 のとき `calibration_rounds`）を追加（Q8）。
- `run_mc` / `run_mc_with_rng` は系列を検査して `Result<_, SessionError>` を返す（設計書は `McResult` を直接返す）。`run_mc_with_rng` は `batch_row_rng` の返り値を渡すために追加。
- `m4.budget_ratio >= 1.0` は予算なし（`None`）。
- `RingSectorCell.n_recv` は受信済み全体（受信のみ・内部・外部・両方）。`n_int`・`n_ext`・`n_both` は互いに排他の分類で、`n_int + n_ext + n_both <= n_recv`。
- `Session::step` の分位点は昇順の添字 `round((n-1)q)`（`f64::round`＝四捨五入、0.5 は切り上げ）。
- `batch_toml` は `ip_sampling = {size = 1, seed}` を出す（バッチは IP を指定できない）。`num_rounds` は `calibration_rounds`（バッチでは系列長と較正 T を兼ねる）。`user_sampling.size = user_index + 1`。出力の文字列は結合文字を含むパスに対応するため自前でエスケープする（`{:?}` は TOML で不正になる）。
- ブランチツリーは P3 まで 1 本の鎖（節 id = ラウンド）。`Session` は `rng_before` を保持しており、`rewind_to` は P3 で実装する。
- `centrality::metric_from_csv`（VC 等の事前計算 CSV）は列名 `node, degree, pagerank, vc`、カンマ区切り、ヘッダーの有無どちらでも可（Q9 の仮置き）。

# 修正: ノードとエッジの位置のずれ（2026-10-02）

- **症状**（ユーザー報告）: パン・ズームでノード（WebGL）とエッジ（Canvas2D）が分離して見え、止めても戻らない（Retina の Mac）。
- **原因**: 頂点シェーダが y を反転していた（`vec2(u_zoom, -u_zoom)`）。NDC もワールドも y は上向きなので不要で、反転が要るのは y が下向きの Canvas2D だけ。WebGL のノードが画面中心で上下ミラーされ、縦にパンするほど逆方向にずれた。DPR には依存しない。
- **見逃した経緯**: P1 の確認中に「IP の画面位置が 2D の計算と約 10px 違う」「ノードのクリックが外れる」ことがあったが、テスト座標のずれと判断していた（誤り）。初期表示は対称に近く、静止画の目視では気付けなかった。
- **修正**: `render/shaders.ts` の 1 行。再発防止に `npm run e2e:align`（`web/scripts/check-alignment.mjs`）を追加。開発時のみ公開する `window.__glProbe`（描画結果のピクセルを読む）で、Canvas2D と同じ式の位置に WebGL のノードが描かれていること、上下ミラー位置には無いことを、DPR 1・2 で、初期表示・パン・ズーム後に全ノード分確認する。
- **結果**: 修正前は 23 件不一致（初期表示で 100 ノード中 85 個がずれ）→ 修正後は全件一致。Retina（DPR 2）でのパン後のスクリーンショットで、エッジがノードに接し、リングの中心が IP に合っていることを目視確認。IP を見た目の位置でクリックして選択できる。

# 修正: 到達不能ノードが巨大な四角形の塊になる（2026-10-03、デスクトップ版・Web 版）

- **症状**（ユーザー報告、デスクトップ版のスクリーンショット）: 選んだ IP とその周りのほかに、ノードが四角形の塊になって画面の大半を占める。
- **原因**: 個別表示（展開していない状態）で、IP から到達できないノードも描いていた。到達不能のノードは外側の格子（設計書 7.8 の 5。間隔 0.35、ノード数の平方根の列数）に置くため、数千ノードあると巨大な正方形になり、カメラもそこに合わせて IP が小さくなった。設計書は「全体図では 1 つの枠にまとめ、展開するときに格子状に並べる」としており、展開していない個別表示で全ノードを出す想定が不適切だった（要件 N03 の「全ノードを個別に表示」は到達可能なノードに限る方針に改める）。
- **修正**: 展開していないときは、IP から到達できるノードだけを描く（辺も、両端が描画対象のものだけ）。カメラもその範囲に合わせる。到達不能ノードの件数と「表示する」ボタンを上部に出し、押すと従来の格子として展開する（上限 10,000 ノード。超えるときは範囲を狭めるよう表示）。Web 版・デスクトップ版の両方。Web の `e2e:align` は到達不能ノードを検証の対象から除いた。
- **確認**: IP の到達範囲が小さい 4,000 ノードの合成グラフ（IP から 20 ノードのみ到達）で、デスクトップ版（Retina）と Web 版（ヘッドレス Chrome）のスクリーンショットを目視。IP と周りだけが表示され、「3,980 個は表示していません」の案内が出る。「表示する」で展開できる。IP のクリック選択も動作。`cargo test`（workspace）・`cargo clippy -p desktop`・`npm test`・`npm run e2e:align` は通過。
- **ついでの修正**: デスクトップ版の「ms/frame」は再描画の間隔（待機を含む）で、止まっているときに大きく見えた（137 ms など）。UI 処理の実時間（「UI 0.3 ms/フレーム」）に変更。

# P3（巻き戻し・分岐 / MC 併記 / 動画・画像 / 2 画面比較）の追記（2026-10-03）

## sim-api（P3-1 の核）
- `Session` に保存点（ラウンド 0 と 8 ラウンドごとの `Population`・`SimRng`・`sent`・`cum_xact` の複製）、`BranchTree`（`tree.rs`。節 `{id, parent, round, choice, summary}`、根 = 0）、現在の枝（`path`）を追加。`rewind_to(r)` は保存点を復元し、記録済みの選択を `NoTrace` で再生する（`step` と共通の `apply_round`）ので乱数も復元され**ビット一致**。`switch_to(id)` は共通の祖先まで巻き戻し、その枝の選択を `step` で再生。`step` は同じ選択の子があれば節を再利用（枝が増えない）。`ever_flags_at(r)`、`summary_at(r)`、`tree_view()`（`lane` = 段は Rust 側で決め、両版が共有）。`load_tree`／`ScenarioRecord::restore_tree` で記録 JSON から木全体を復元。`export` の `branch_tree`・`active_path` は実際の木になった。
- **T-15**（`sim-api/tests/rewind.rs`、4 件）: 機構なし・あり（m∅ 含む）で、k = 0・1・7・8・9・15・16・17・19 に巻き戻し → 状態（`Population` の全フィールドの `to_bits`）・ログ・イベント列・要約・乱数の次の出力が、最初の k ラウンドだけ回した別セッションと一致、残りを再生すると元の最終状態と一致。別の選択で分岐 → `switch_to` で元の枝・分岐の枝のどちらへ戻っても一致。同じ選択の再発信で節が増えない。`rewind_to` が先のラウンドなら `Err`。M4 の予算（`sent`）も巻き戻る。記録 JSON の往復で木・現在の枝・状態が一致。

- 互換性: 古い記録 JSON・設定 TOML の `m2`〜`m5`・`horizon` は知らないキーとして無視して読める（テスト `default_toml_parses_and_validates`）。系列文字列の `-` は不正な文字になる。
- 不変条件: M1 を無効にしたときの `core::diffusion` とのビット一致（T-01・T-02・T-07）は維持。ゴールデン（`spec/fixtures/golden_*.json`）は balanced を M1 のみで作り直した。
